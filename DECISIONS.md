# Decisions and framework gaps

Running log. Where SPEC.md and the framework disagree, the framework wins and the conflict is recorded here.

## D-001 Framework consumption
Git submodule at `framework/`, pinned to `356cfc8` (master, includes 004 blob sync). The repo root is an npm workspace
over `framework/packages/*`, so `@sync/*` resolve to the framework's TypeScript source (as in its own sample app).
`tsconfig.json` repeats the framework's `paths` with a `framework/` prefix.

## D-002 Svelte and app-build (SPEC 10.2, option 1)
`ui/` is built with Vite in library mode to `ui/dist/ui.js` (exports `mount(target, api)`); the `daycare` module's root
view imports that file. Component CSS is `css: 'injected'` so the one file is self-contained. `npm run build` runs
`build:ui` first. No upstream change to app-build needed.

## D-003 Inline theme script is not allowed (SPEC 6.2)
The generated CSP is `script-src 'self' blob:`, so an inline pre-paint script would be blocked. The same logic ships as
`public/theme-init.js` (listed in `assets`, loaded synchronously at the top of `<body>`). `ui/src/lib/theme.ts` mirrors it.

## D-004 Banned imports in app code (SPEC 8, 10.1)
`app-build` bans value imports of `@sync/core` and `@sync/spaces` from app files, including `app.config.ts`, which the spec
said may use them. Consequences:
- `assertSecureCore(core)` can't be called from app code; the secure-core test will live in `tests/` instead.
- The authz validator (`modules/daycare/authz.ts`) will import only types, and is registered through the `core` object
  handed to the `blobs({ core, spaces })` hook / `onReady` (`core.registerValidator` exists). No framework change needed.
Revisit in phase 2 if role lookup from inside a validator proves impossible (SPEC 3.3).

## D-005 Local tooling
- `fast-check` is a root devDependency because `@sync/testkit` needs it and the framework's own devDeps aren't installed.
- Docker is not installed on the dev machine. `relay/` has a Dockerfile and compose file for the Unraid host; locally use
  `npm run relay` (ws://localhost:8787, set `BLOB_DIR=./blobs` for attachments).
- The relay Dockerfile builds from `framework/` with its own lockfile.

## D-006 Placeholder art
Icons are generated by `npm run icons` (original cream cloud on teal). Replace with real artwork later.

## D-007 Authz validator (SPEC 3.3): feasible, no framework change needed
`modules/daycare/authz.ts` implements `daycare-authz`. It resolves device -> user -> role with `spaces.members(space)`
(cached per Space, cleared on `member:changed`), defers when the device is unknown, and uses `ctx.existing` for ownership.
It is structural (imports nothing from @sync/*) and registered in `app.config.ts` inside the `blobs({ core, spaces })`
hook, which runs before transports start, so it is in place before any remote packet arrives.
Beyond the spec, as hardening (enforced for providers too):
- **Provenance on create:** `createdBy` must equal the author's user and `createdByRole` the role implied by their
  membership (Owner = provider, Editor = parent). Without this a parent could post as a provider.
- **Frozen fields on parent updates:** `kind`, `child`, `createdBy`, `createdByRole` (so a parent's note can't become a nap).
- Default deny for any type or operation not listed. Viewers are rejected for all daycare writes.
Tested with fakes (tests/unit/authz.test.ts) and on real encrypted nodes (tests/contract/authz.integration.test.ts), where a
modified parent client without the validator is rejected by the provider and an observer. Mutation-checked: removing the peer
validators makes the forgery tests fail.

## D-008 Schemas (SPEC 5)
All seven types are in `modules/daycare/schema/`. `objectCheck` on `entry` requires the kind-specific fields. Choices:
- Staff `settings` gained `sinceThresholdMinutes` (default 180) for the configurable amber chip (SPEC 6.3).
- Bottle `ozFinished` may not exceed `ozOffered`; oz values are multiples of 0.5.
- `objectCheck` is create-only (framework rule), so later updates are not re-checked against kind rules.
- Deterministic reaction IDs are deferred to phase 6 with the UI that creates them.
- The photo kind's positive case needs a real blob reference, so it is exercised with the attachments work in phase 7.
- Blobs are switched on now (500 MB budget) because the schemas have blob fields; the hook is shared with the validator.

## D-009 Framework gap: join and link approval (SPEC 4.3, 4.5) — upstream PR
`startApp` opened the secure core without `approveJoin`/`approveLink`, whose default is to refuse, so invites with
`approval: 'required'` and device links could never complete in an app-build app. Fix: two optional `AppConfig` fields
passed through to `openSecureCore` (about 10 lines + a test). Raised as
[epl692/Sync-PWA-Framework#4](https://github.com/epl692/Sync-PWA-Framework/pull/4); `framework/` is pinned to that
branch's commit (`4200397`) until it merges. **After it merges, move the submodule pin to master.**
The app answers through `modules/daycare/bridge.ts`: the UI registers an approver (the SAS dialog); with none mounted the
answer is "no".

## D-010 How the UI reaches Spaces
The module declares `access: { spaces: { read: 'any', write: 'any', manage: true } }`, which puts the full Spaces API on
`ctx.spaces.admin`. The UI sees it through structural types (`ui/src/lib/types.ts`), never framework imports. QR drawing
(`qrToSvg`, from identity-invite) reaches the UI via the bridge, shown as an `<img>` data URL, not `{@html}`.
All onboarding logic is `ui/src/lib/service.ts`, tested on real encrypted nodes.

## D-011 Onboarding design choices
- **Which Space is which:** by name suffix (" Staff", " Family"). A device is a provider when it owns a Staff Space, a
  parent when it only holds family Spaces. Only affects that device's own UI; authority comes from the Space itself.
- **Membership lags the join:** `spaces.list()` omits a Space until the device has synced its own join event, so the join
  screen waits (up to 30s) for it before showing a home screen.
- **Second provider:** joins the Staff Space as Owner (always needs approval). Access to families is by single-use
  `approval: 'auto'` Owner invites left in the Staff Space as `daycare.staffInvite` (deterministic id per provider+family, so
  two devices converge) and accepted automatically. The inviting device must be online; the receiver retries every 30s and a
  fresh invite is issued once one expires. `staffInvite` gained `expiresAt` for this.
- **Relationship:** stored in the display name, "Erin (Mom)", so providers see it in member lists.
- **Invite links:** `<page URL>#/join/<payload>`. On open the hash is removed from the address bar and kept in memory.
- **Tracking my invites:** the framework can't list invites, so each device remembers the ones it made (localStorage) to
  show and cancel them.
- **Relay URL** is a build constant (`RELAY_URL` in `constants.ts`) because the CSP `connect-src` must list it.
  A runtime override in Settings is deferred; it could only work for origins the build already allows.

## Deferred from phase 3
- WebRTC peer-to-peer fallback (its pairing is a manual code exchange; needs its own UI) and in-app QR scanning
  (phone cameras open the link directly; pasting works today).
- Removing a provider (Staff Space) and per-device revocation UI; the service has `removeMember`/`revokeDevice`.
- Install hint is basic (Chrome prompt, iOS instructions).
